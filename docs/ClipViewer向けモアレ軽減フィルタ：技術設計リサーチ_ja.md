# ClipViewer向けモアレ軽減フィルタ：技術設計リサーチ

## 結論（TL;DR）
- **最重要の発見：WPFの`ShaderEffect`（HLSLピクセルシェーダー）単体では、ダウンスケール時のモアレを軽減できない。** なぜなら、シェーダーはUI要素が**既にラスタライズ済み**のビットマップ（レイアウト/レンダリングサイズ）を後処理するだけであり、網点パターンはシェーダーが動作する前にWPFによって既にダウンサンプリング（＝エイリアシング）されてしまっているため。正しいアーキテクチャは「ダウンサンプリング→（任意で）シャープ化」の2段階パイプラインである。表示サイズ近くまでの縮小は適切なマルチタップフィルタ（WICのデコード時縮小、および／またはCPU SIMDによるLanczos/エリア平均リサンプラ）で行い、WPF／GPUは安価な後処理と表示にのみ使う。
- **推奨する主要フィルタ：2倍以上の縮小にはエリア平均（ボックス）ダウンスケール、端数分の最終ステップには広いサポート幅のLanczos-3を併用し、これを「ダウンスケール時のみ」適用する。** 網点によるモアレは本質的に「間引き（decimation）前のローパス処理」の問題であり、間引き前の強いエリア平均／Lanczosローパスこそがこれを除去する。これは必ずダウンスケール時のみに限定し、等倍表示やズームインでは絶対に適用しないこと。ユーザー選択可能な3〜4モード（オフ／高速／高品質／強力デスクリーン）と強度スライダーを用意する。
- **ページめくりのリアルタイム性能を確保するには、デコード時に縮小（`BitmapImage.DecodePixelWidth`）して縮小済みビットマップをキャッシュし、隣接ページはバックグラウンドスレッドでプリフェッチする。** GPUシェーダー（WPFの`ShaderEffect` ps_2_0、あるいは純粋な.NET Framework WPFから離れられるならWin2D／ComputeSharp）は、コアのダウンスケーラーとしてではなく、オプションの追加デスクリーン／シャープ化パスとして活用するのが有効。

## 主な調査結果

1. **アーティファクトの原因。** 漫画のスクリーントーンは規則的な網点グリッド、すなわち高周波の周期信号である。表示側が多数のソーステクセルを1つの出力ピクセルへマッピングする際（＝ダウンスケール）、十分なローパス（アンチエイリアス）事前フィルタを適用しなければ、出力側のナイキスト限界を超える周波数成分が「折り返し（エイリアシング）」を起こし、低周波のうねりパターン＝モアレとして現れる。これは印刷物の網点をスキャンする際に生じる「ハーモニックビート」と同じ現象である。標本化定理が要求する修正方法は、間引く**前**に帯域制限（ぼかし）を行うことである。

2. **WPFアーキテクチャの落とし穴。** WPFの`Image`のデフォルトスケーリングは.NET 4.0で変更された。Microsoft PM の Pete Brown は LearnWPF（2010年12月）で「.NET 4のリリースに伴い、MicrosoftはRenderOptions.BitmapScalingModeのデフォルト値をHighQualityからLowQualityへ変更した」――つまりFantからバイリニア（`Linear`）へ変更したことを記している。バイリニアは貧弱なローパスであり、Avery Lee（VirtualDub作者）が指摘するように、WPFのバイリニアは「2x2カーネルに限定され、ミップマップを使用しないため、70%程度以下の縮小率でエイリアシングが始まる」。`RenderOptions.BitmapScalingMode="HighQuality"`（＝`Fant`）に設定することでGPUコストを抑えつつ改善できるが、その上にカスタム`ShaderEffect`を重ねても、シェーダーはWPFが既にスケーリングした後の「出力ピクセルにつきほぼ1サンプル」しか見ていないため、失われた detail を回復できない。

3. **網点モアレに対するアルゴリズムのランキング。** ソース全域にわたるエリア平均（ボックス）と広いサポート幅のLanczosが、従来型ローパス・ダウンスケーラーとして最も効果的。ガウシアン事前ぼかし＋間引き＋軽いシャープ化は、スキャン業界由来の古典的な「デスクリーン」レシピ。バイキュービック／Mitchell–Netravaliは中間的な選択肢。最近傍法や単純なバイリニアが最も劣る。周波数領域（FFTノッチ）やML手法は最高品質だが、リアルタイムのページめくりには到底速度が足りない。

4. **性能面での経路。** `BitmapImage.DecodePixelWidth`を使うと、JPEG／PNGのコーデックが**縮小サイズへネイティブにデコード**する（WIC経由）ため、最速かつ高品質な縮小手段となり、メモリ消費も大幅に削減できる。これはビューワの基盤として最適。CPU SIMDリサンプラ（JPEGViewの実装など）は500万画素のLanczosリサイズを約40msで処理する。ImageSharpやMagicScalerといった管理コードのライブラリも選択肢となる。

## 詳細

### 1. なぜスクリーントーンはダウンスケール時にモアレを生むのか
モアレパターンとは、周波数が近い2つの反復パターンが重なった際に生じる干渉アーティファクトである。漫画では、スクリーントーンの網点グリッドがリサイズ時の出力側サンプリンググリッドと相互作用する。ナイキスト・シャノンの標本化定理に従えば、忠実なダウンサンプリングにはピクセルを間引く**前**に2次元ローパス（アンチエイリアス）フィルタを適用する必要があり、そうしなければ高周波の網点detailが折り返って低周波の帯状パターンとして現れる。ハーフトーン／スクリーントーン画像は、画像処理分野の特許文献や論文において、ダウンスケール時に「特に脆弱」であると明記されている。このアーティファクトは間引きの**瞬間**に生成されるため、事後のピクセル空間での色補正では完全には除去できない――情報は既に破壊されている。だからこそ「ぼかし→間引き」という順序は譲れないのであり、表示後段のシェーダーがアーキテクチャ的に誤ったアプローチである理由もここにある。

### 2. WPF特有の実装事情

**ShaderEffect／HLSLピクセルシェーダー。** WPFは`ShaderEffect`クラス（`System.Windows.Media.Effects`）を通じてGPUピクセルシェーダーを公開しており、`UIElement.Effect`プロパティ経由でアタッチする。HLSLの`.fx`は`fxc.exe /T ps_2_0`で`.ps`バイトコードリソースへコンパイルされ、パラメータは`PixelShaderConstantCallback`で登録された依存関係プロパティ経由で流れ、入力画像は`RegisterPixelShaderSamplerProperty`で`s0`として登録される。ここで重要な制約は以下の通り：

- **WPFが受け付けるのは`ps_2_0`バイトコードのみ**（クラシックビルドではps_2_a／2_bやps_3_0はWPFローダーに拒否される。ps_3_0は後期ビルドで部分的にサポートされるがソフトウェアフォールバックがなく、`RenderTargetBitmap`では無視される）。Microsoft Learnのps_2_0リファレンスによれば、このプロファイルは「命令スロット合計：96（算術64・テクスチャ32）」を許容する。アセンブリプロファイル自体は16個のテクスチャサンプラを許可するが、**WPFの`ShaderEffect`ラッパーはさらに制限が厳しく**、公開されるサンプラ入力は一般的に4個程度とされ（クラシックビルドの場合）、マネージドコードから到達できるのは`S`と`C`のレジスタ型のみである。これにより畳み込みに使えるカーネル幅が大きく制限される。
- **決定的な制約：** シェーダーは要素の**既にラスタライズ済みのレンダリング/レイアウトサイズのテクスチャ**上で動作し、出力ピクセルにつきおおよそ1つのソーステクセルしかサンプリングしない。したがって、適切にアンチエイリアスされたダウンスケーリングに必要な多数のソーステクセルの統合はできず、エイリアシングは既に焼き込まれてしまっている。これはWPFの`ShaderEffect`ドキュメントや、Walt Ritscherの著書『HLSL and Pixel Shaders for XAML Developers』（O'Reilly）で、シェーダー入力を「ラスタライズ済みのWPFテクスチャ」と説明していること、またPDC 2008のWPFグラフィックス講演（David Teitlebaum）でシェーダー1回の呼び出しにつきテクスチャを1つ入力し1つ出力すると説明されていることからも裏付けられる。
- ミップLOD選択に必要な`ddx`／`ddy`の微分命令は`ps_2_0`では確実には利用できず、WPFはテクセルサイズを専用レジスタ（`DdxUvDdyUvRegisterIndex`）経由で渡している。
- ShaderEffectはサブツリーを中間レンダーターゲットへ強制的に描画させるため、従来フレームごとの割り当てオーバーヘッドが問題視されてきた。複雑なシェーダーはWPFのソフトウェアパスで10fpsを下回ることもある。

**結論：** `ShaderEffect`は、適切なリサイズの**後**に行う安価な全画面後処理（軽いアンシャープマスクやデスクリーン用の軽微なぼかしなど）にのみ使うべきであり、主要なダウンスケーラーとして使ってはならない。

**BitmapImageのデコード時縮小（高速化の鍵）。** `BitmapImage.DecodePixelWidth`（または`DecodePixelHeight`）を設定すると、**JPEGおよびPNGコーデックがネイティブに指定サイズへデコードする**。他のコーデックはフルサイズでデコードしてから縮小する。Microsoftのドキュメントは「画像がデコードされる幅（ピクセル単位）を取得または設定する」プロパティであり、「JPEGおよびPortable Network Graphics（PNG）コーデックは、指定サイズへ画像をネイティブにデコードする。他のコーデックは元のサイズで画像をデコードし、その後希望のサイズへスケーリングする」と説明している。アスペクト比を保つには片方の次元のみ設定する。`BitmapCacheOption.OnLoad`＋`Freeze()`と組み合わせることで、ソースストリームを解放しつつクロススレッドでのプリフェッチが可能になる。これは容易に実現できる高品質な縮小手段（コーデックレベル、WIC経由）であると同時に、メモリ効率も圧倒的に優れている――MicrosoftのWPFサンプル自体が、これを設定しない場合「アプリケーションは実際に表示されるサイズではなく、通常サイズでレンダリングされたかのように画像をキャッシュしてしまう」と注記している。大量画像コレクションのページめくりには不可欠。

**WPF標準スケーリングモード。** `RenderOptions.BitmapScalingMode`は`NearestNeighbor`、`LowQuality`／`Linear`（バイリニア、.NET 4以降のデフォルト、GPUアクセラレート）、`HighQuality`／`Fant`（より高品質なエリア平均的フィルタ）を提供する。列挙値のエイリアスは文字通り`Fant = 2, HighQuality = 2, Linear = 1, LowQuality = 1, NearestNeighbor = 3, Unspecified = 0`である。WPF内部の`TransformedBitmap`スケーラは、WICのFantモードにハードコードされている（Microsoft の Dwayne Need による）。`Fant`は`Linear`と比べてモアレを明確に軽減し、コストも低いため、カスタムパイプラインを望まないユーザー向けの妥当な「フィルタON」のベースラインとなる――ただしこれは渡されたビットマップに対して合成時に適用されるものであるため、デコード時縮小と組み合わせるのが最善である。

**Direct2D／Win2D／ComputeSharp相互運用。** 真にGPUによるマルチタップダウンスケーリングを行うには、フル解像度のソースを明示的にシェーダーへ供給し、制御されたターゲットへレンダリングする必要がある：
- **D3DImage + SharpDX**は、Direct3D 9/10/11コンテンツをWPFの`ImageSource`としてホストする。`D2dControl`（dalance）はすぐ使えるWPF+SharpDX製Direct2Dコントロールである。SharpDXはアーカイブ済み（保守終了）だが.NET Framework 4.6では動作する。
- **Win2D**（`CanvasControl`、`PixelShaderEffect`）や**ComputeSharp.D2D1**（Sergio Pedri）は、C#でD2D1ピクセル／コンピュートシェーダーを記述可能にし、適切なマルチタップサンプリング（`D2DSampleInputAtOffset`）とミップサポートを提供する――ただしこれらはUWP／WinUI／モダンWindowsランタイムを対象としており、**クラシックな.NET Framework 4.6のWPFは対象外**である。したがって採用には相互運用レイヤーの構築、あるいはフレームワーク移行が必要となる。この点は移行判断事項としてフラグを立てておく。

### 3. 候補アルゴリズム

- **エリア平均（ボックス）フィルタ：** 各出力ピクセルの範囲下にあるすべてのソーステクセルを平均する。シンプルかつ高速で、ダウンスケーリングにおいてはほぼ最適なアンチエイリアシングとなる――OpenCVのドキュメントは`INTER_AREA`について「モアレのない結果が得られるため、画像の縮小には好ましい手法である場合がある」と述べている。ややソフトな仕上がりになるが、大幅な縮小やモアレ除去のベースとして最適。**網点対策としてコスト対品質が最良。**
- **Lanczos（窓付きsinc、a=2または3）：** 理論上ほぼ理想的なローパスであり、ダウンスケール時に最もシャープな detail 保持と強いエイリアシング抑制を両立する。カーネルが大きいほどコストが増し、硬いエッジ（線画）でリンギングが生じうる。「高品質」オプションとして優秀。JPEGViewの「NoAliasing」ダウンスケールモードはシャープ化=0のLanczosである。
- **ガウシアン事前ぼかし→間引き→アンシャープマスク：** 古典的なPhotoshop／スキャナの「デスクリーン」レシピ（ぼかし半径≒シャープ化半径、その後USM）。網点パターンを溶かすのに非常に有効で、ぼかし半径によって調整可能。強度スライダー付きの「デスクリーン（強）」モードのよいモデルとなる。
- **バイキュービック／Mitchell–Netravali（B, C）：** Mitchell（B=C=1/3）は中立的な良好なダウンスケーラー。このファミリーの設計上、Bを大きくするとぼける（リンギング減少）、Cを大きくするとシャープになる（リンギング増加）。Catmull-Rom（B=0, C=0.5）はシャープだがリンギングあり、B-スプライン（B=1, C=0）はぼけるがリンギングなし――「ソフト／モアレ抑制寄り」プリセットとして有用。Lanczosより安価で品質も十分。
- **ミップマップ＋トリリニア：** 事前にべき乗2のピラミッド（ボックスフィルタ適用済み）を構築し、表示サイズでミップレベル間をトリリニアブレンドする。GPUコストが低く、時間的に安定しており、3D分野では標準的なアンチモアレ技法である。ズーム／アニメーション対応ビューワに最適。若干過度にぼける。WPFの`BitmapScalingMode`はテクスチャがミップマップを提供している場合にのみそれを使用する（NoesisGUI／WPFのディスカッションによればデフォルトでは提供されない）ため、自前で構築する必要がある（例：Direct2D／Win2D経由、あるいはデコード済みピラミッドレベルをキャッシュする方式）。
- **FFTノッチ／適応ガウシアンノッチフィルタ：** フーリエスペクトル上で網点のピークを検出し、ノッチアウトする（IETの適応ガウシアンノッチフィルタ論文、OpenCVの周期ノイズ除去チュートリアル参照）。既知の周期パターンに対する最高品質のデスクリーンだが、画像ごとにFFTとピーク検出が必要であり、**リアルタイムのページめくりには遅すぎる**。将来「書き出し／静止画」用の高品質モードとして温存する程度に留めるべき。
- **専用の漫画／ML系デスクリーナー：** Screentone-Remover（ガウシアン＋エリア平均ぼかし後にラプラシアンシャープ化）のようなツールや、研究成果（スクリーントーン分離のためのLoG／FDoG、SIGGRAPH-Asia 2022のスクリーントーン保存型リターゲティング）は、いかなる従来型の線形フィルタも網点モアレを完全には回避できないことを裏付けている――ぼかすか、エイリアシングするかの二択である。これらはオフライン／重量級処理であり、ホットパスには不向き。

### 4. 専門ツールの対応方法
- **Photoshop／Sattva Descreen／スキャナドライバ：** デスクリーン＝スクリーン除去＋モアレ軽減であり、実装としては「ぼかし（ガウシアン／メディアン／デスペックル）→ダウンサンプリング→アンシャープマスク」となる。Wayne FultonのScantipsによる古典的な手順は「2倍で解像度スキャン→ぼかし／デスペックル→半分にリサンプリング→USM」である。Sattva Descreenは、スクリーン周波数、CMYKチャンネル別スクリーン角度、「モアレ軽減」トグル、シャープネススライダーを公開している。示唆点：**強度（ぼかし半径）**と**シャープ化**のコントロールを用意すること。
- **JPEGView（David Kleinerによるオリジナル、2007年SourceForgeで公開。sylikcによるフォークあり）：** 高速なWindows用ビューワで、**すべてのリサンプリングをCPU上でAVX2/SSE2を用い最大4コアで実行**する（意図的にGPUを使わない：「AVX2/SSE2アクセラレーションと最大4CPUコアを使用し、ほぼ瞬時の画像読み込みを実現」）。ダウンサンプリングには**分離可能なLanczos**（固定小数点演算：スカラーパスで32ビット、SSEパスで16ビット）を使用し、アップサンプリングは常にバイキュービックである。INI設定で`DownSamplingFilter = BestQuality | NoAliasing | Narrow`（NoAliasing＝シャープ化0のLanczos、エイリアシングがほぼゼロ）と`Sharpen`値（デフォルト0.3）を公開している。開発者自身によるSourceForgeディスカッション内のベンチマーク：非SIMDパスは「SSEを使っていた頃より5倍遅い（500万画素画像で200ms対40ms）」と述べており、**CPU SIMDによるLanczos**がインタラクティブなビューワにとって十分高速かつ高品質であることの強力な実例であり、ClipViewerのフィルタメニューにとって良いモデルとなる。
- **漫画／アニメーションソフト（CLIP STUDIO、Tahoma2D）：** Tahoma2Dは「Resample Balance」ドロップダウン（Standard／Improved／Highに加え、Triangle、Mitchell-Netravali、Cubic convolution、Hann、Hamming、Lanczos、Gaussian、Closest Pixel、Bilinear）を公開しており、「バランスを高く選ぶほど、レンダリングに必要な時間が長くなる」と注記している。これは「複数フィルタのドロップダウン」というUXが業界標準であることを裏付けている。

### 5. 「常時フィルタ適用」対「ダウンスケール時のみ適用」
リサンプリング由来のモアレは本質的に**ダウンサンプリング**（ソース解像度＞表示サイズ）のアーティファクトである。アップスケールや等倍表示時に同じローパスを適用しても、利益なく単に画像がぼけるだけであり、ズームイン時はユーザーは通常、実際のピクセル／網点を確認したいと考えている。専門的な実践では両者を明確に区別している。WPF自体、および一般的なビューワは**アップスケーリング**には最近傍法やバイキュービックを用い、強いローパス（エリア平均／Lanczos）は**ダウンスケーリング**時のみに使う（JPEGViewは「アップサンプリングは常にバイキュービック」とハードコードされており、アンチエイリアシングのLanczosはダウンサンプリング時のみ提供する）。**推奨：モアレフィルタは`ソース解像度＞表示解像度`（つまり縮小率<1.0）の場合にのみゲーティングすること。** ほぼ等倍に近い境界域では、不要なぼかしを避けるため小さな閾値を設ける（例：縮小率<約0.95の場合のみ発動）。ゲーティングはデフォルトで自動とし、常時適用したいユーザー向けにオプションのオーバーライドを用意する。

| 最近傍法 | 非常に悪い（最悪のエイリアシング） | 最速 | 可（BitmapScalingMode） | 極めて低い |
| バイリニア（Linear、WPFデフォルト） | 縮小率約70%以下で悪化 | 非常に高速（GPU） | 可（標準搭載） | 極めて低い |
| Fant／HighQuality（WPF標準） | 良好、低コスト | 高速（GPU／コンポジタ） | 可（標準搭載） | 極めて低い |
| エリア平均（ボックス） | 優秀（ローパスの基本） | 高速（CPU／デコード時） | 部分的（真のGPU化にはD2D/Win2D要） | 低い |
| Lanczos-3（分離可能） | 優秀、シャープ | 中程度（CPU SIMDで約40ms/500万画素） | 部分的（カスタムシェーダー／Win2D要） | 中程度 |
| ガウシアン事前ぼかし＋USM（デスクリーン） | 優秀、調整可能 | 高速〜中程度 | ぼかしはGPUで安価、リサイズはCPU/デコード時 | 低〜中程度 |
| バイキュービック／Mitchell（B, C） | 良好 | 高速 | 部分的 | 低〜中程度 |
| ミップマップ＋トリリニア | 非常に良好、安定 | 構築後は非常に高速 | 可（D2D/Win2D経由、ピラミッドは自前構築） | 中程度 |
| FFTノッチフィルタ | 既知パターンには最良 | 遅すぎる（リアルタイム不可） | フレーム内実行は非現実的 | 高い |
| ML／専用デスクリーナー | 総合的に最良 | 遥かに遅すぎる | 不可 | 非常に高い |
| WPF ShaderEffect単体をダウンスケーラーとして使用 | **効果なし**（スケーリング後のビットマップしか見えない） | 速いが誤ったアプローチ | 該当なし | 中程度（かつ方向性が誤り） |

## 推奨事項

**ステージ1 — アーキテクチャ（最優先で着手）。** WPFの合成スケーラーから切り離した2段階パイプラインを構築する：
1. **デコード時縮小：** 各ページを`BitmapImage`として読み込む際、`DecodePixelWidth`を表示幅程度（あるいは直近上位の2のべき乗）に設定し、`CacheOption=OnLoad`とした上で`Freeze()`する。これによりWIC経由の高速・低メモリ・高品質な第一段階の縮小が得られ、隣接ページのバックグラウンドプリフェッチも可能になる。
2. **最終的な高品質リサンプリング（ダウンスケール時のみ）：** デコード済みビットマップがなお表示サイズより大きい場合、CPU SIMDリサンプラを実行する――**縮小率の整数部にはエリア平均、端数部にはLanczos-3**を用いて、正確な表示サイズのビットマップを生成する。(ページ, 表示サイズ, フィルタ, 強度) をキーにキャッシュする。表示は`Image`で`BitmapScalingMode=NearestNeighbor`（既に等倍なので）または`HighQuality`を使う。

リサンプラは、手作りのSIMDカーネルをプロファイリング結果が要求しない限り、**ImageSharp**（管理コード、Lanczos／エリア平均／Mitchellを標準搭載。ただし商用ライセンスの閾値に注意）や**MagicScaler／Magick.NET**の利用を検討する。`.clip`ファイルについては、ファイル内のSQLiteデータベースに埋め込まれたPNGプレビューを読み取る（`SQLite format 3`ヘッダーを探索し、サムネイル／キャンバスblobを読み取る。jercos/clipthumbやHydrusの実装と同様の方式）か、PSD／PNG／JPEG書き出しを要求する。`.clip`のフルレイヤーレンダリングは対象外とする。

**ステージ2 — フィルタ機能とUI。** **フィルタ種別のドロップダウン**、**オン／オフトグル**、**強度スライダー**を公開する（Tahoma2D／CLIP STUDIO／JPEGView、および写真フィルタのUXガイドラインに準拠した業界標準的UX――アルゴリズム選択にはドロップダウン、強度にはスライダー、ライブプレビュー）：
- **オフ** — 最近傍／バイリニア、等倍。
- **高速** — WPFの`Fant`／HighQuality（GPU、ほぼコストなし）。
- **高品質（デフォルト）** — 上述のエリア平均＋Lanczos-3パイプライン。
- **デスクリーン（強）** — ガウシアン事前ぼかし（半径＝強度）＋間引き＋アンシャープマスク。強い網点向け、最もソフトな仕上がり。

スライダーの意味：デスクリーンではぼかし半径／シャープ化にマッピングし、Lanczosではフィルタサポート幅／シャープ化にマッピングする（JPEGViewの`Sharpen`と同様の考え方）。ライブのビフォーアフタープレビューを提供し、ユーザーごとのデフォルト設定を記憶する。

**ステージ3 — ゲーティング。** モアレフィルタは**縮小率<約0.95**（ダウンスケール時）のみ適用する。アップスケーリング／ズームインにはバイキュービックを使用し、等倍時は決してフィルタしない。上級者向けに「常時適用」オーバーライドを用意する。

**ステージ4 — 任意のGPU仕上げ。** リサイズの**後**に、軽量な`ShaderEffect`（ps_2_0）でオプションのGPUアンシャープマスクや軽度のスムージングを追加し、強度コントロールの一部として公開する。純粋な.NET Framework WPFから離れる決断をした場合（Win2D／ComputeSharp採用時）にのみ、マルチタップのデスクリーン／ミップマップダウンスケール全体をGPUで行うことを検討すべきである。

**方針を変更すべきベンチマーク条件：** プロファイリングの結果、1ページあたりのデコード＋リサンプル処理がページめくりのレイテンシ予算（プリフェッチ込みで目安1ページあたり50〜80ms未満）を超える場合は、(a) キャッシュをより積極的に行い、プリフェッチページ数を増やす、(b) 最終のLanczosステップを省いてエリア平均のみ、または`Fant`にする、(c) `DecodePixelWidth`を実際の表示サイズにより近づける、のいずれかを検討する。ズームアニメーションに対応する必要がある場合は、そのモードのみ事前構築済みの**ミップマップ＋トリリニア**パス（Win2D／D2D）に切り替える。

## 留意事項
- **「ShaderEffectはダウンスケーラーとして機能しない」という結論が本レポートの核心的な主張である。** WPFの`ShaderEffect`ドキュメント、Ritscherの著書、PDC 2008のWPFグラフィックス講演によって裏付けられているが、「WPFのスケーリング後のテクセルを出力ピクセルにつき1つしか見ない」という正確な挙動は`Effect`のレンダーターゲットサイジングの実装によって変動しうる。実装着手前に、既知の畳み込みを適用してスケーリング前後どちらのデータが見えているかを検証する簡易プロトタイプで確認することを推奨する。
- **従来型の線形フィルタでは網点モアレを完全には除去できない**――シャープさ（ぼけ）と残存エイリアシングのどちらかを犠牲にするトレードオフとなる。この点は研究（SIGGRAPH-Asia 2022のスクリーントーン保存型リターゲティング、CVPR 2021の漫画修復研究）でも根本的な制約として確認されている。強度スライダーによってユーザー自身がこのトレードオフを選択できるようにする。
- **Win2D／ComputeSharp／PixelShaderEffectはUWP／WinUIを対象としており**、クラシックな.NET Framework 4.6のWPFは対象外である。GPUによるマルチタップダウンスケーリングにこれらを使うには、相互運用レイヤーの構築かフレームワーク移行が必要となる。SharpDX（D3DImage／Direct2D相互運用向け）はアーカイブ済み（保守終了）だが、.NET Framework 4.6上では依然として動作する。
- **JPEGViewのソースレベルの詳細**（整数演算の精度、ダウンサンプリングへのLanczos採用、約40ms/500万画素という数値）は、プロジェクトの開発者ディスカッションおよびREADMEに基づくものであり、`BasicProcessing.cpp`の逐行的な精査によるものではない。強い根拠ではあるが、間接的な情報として扱うこと。
- **ImageSharp**は2022年6月に導入された収益閾値を超えると有償の商用ライセンスが必要になる。出荷前にライセンス条件を確認すること。`.clip`の解析は文書化されていないSQLite構造に依存しており、CELSYSによってバージョン間で変更される可能性がある。
- 性能に関する数値は引用元のベンチマーク／ディスカッションに基づく参考値であり、ClipViewerの想定ターゲット環境で実測したものではない。実機での代表的なマシンでのプロファイリングを推奨する。
