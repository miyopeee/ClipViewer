## 1. バージョン変更履歴

### v0.1（草案フェーズ）
- Phase1〜4の初期計画を策定
- 実際の実装とは大きく乖離しているため参考価値は低い

### v0.5.x（基礎機能整備フェーズ）
各バージョンの詳細な機能リストは`ClipViewer_統合要件定義書.md` の「機能一覧」参照。  
以下は特記すべき経緯のみ。

- **基本ビューア**: `.clip` / `.psd` / `.jpg` / `.jpeg` / `.png` / `.webp` / `.gif` 対応
- **GIF再生機能**: F5/F6/F7/F8 キー割り当て、ループ/自動送りモード
- **情報パネル**: `InfoDisplayMode` enum（Off / Basic / Detailed）3状態
- **回転・反転**: `ImageTransformContainer` に `ScaleTransform + RotateTransform` を重ねた実装
- **状態保存**: ウィンドウ位置・表示モード・見開き状態等を ini に保存して再起動時に復元
- **ファイル操作**: ごみ箱削除（`Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile`）、ファイルコピー保存、名前を付けて保存

### v0.8.12（2026/07/28）
- **ドラッグ移動（パン）の範囲制限** — 従来は無制限で、画像を画面の遥か彼方まで飛ばせてしまった。`ClampPan()` を新設し、`Window_MouseMove`（ドラッグ中）・`ApplyZoom`・`Window_SizeChanged` で適用
  - 判定は `content.TransformToVisual(RootGrid).TransformBounds(...)` の**変換後バウンディングボックス**で行うため、回転・反転・見開き・回転FIT補正すべてに自動追従する（個別対応不要）
  - 得られた矩形は現在の `ZoomTranslate` を含むので、`bx = r.X - ZoomTranslate.X` で平行移動ゼロの基準位置に戻してから可動域を求めるのがポイント
  - 可動域の端点は `-bx` と `vw - bx - r.Width` の2つ。**画像が画面より大きい/小さいで大小関係が入れ替わる**ため、min/max を取る `ClampToRange()` で両ケースを同じ式で処理する
  - 実測検証: ①Fit（画像1000x750 / 画面1424x750）で右下へ大きくドラッグ → 横は中央212px→424pxで右端がぴったり画面端に一致して停止、縦は画面と同寸のため完全固定 ②188%ズームで両方向に大きくドラッグ → 黒帯の出現率0%（＝常に画面全体を画像が覆う）
- **🚨 検証ノウハウ（重要な失敗）**: WPF アプリのマウス操作は **PostMessage（WM_MOUSEMOVE/WM_LBUTTONDOWN 等）では届かない**（キー入力は届く）。実入力注入（`mouse_event` + `SetCursorPos`）が必要だが、**対象ウィンドウが最前面でないと他アプリにクリック・ドラッグが飛ぶ**（実際にユーザーのアプリへドラッグを撃ち込む事故を起こした）。必ず ①`SetWindowPos(HWND_TOPMOST)` で最前面固定 ②`GetForegroundWindow` と `WindowFromPoint` の両方で対象ウィンドウを確認 ③不一致なら中断、の順で行う。撮影は PrintWindow（z順に依存しない）
- **PowerShell の関数名 `LP` は禁止** — 組み込みエイリアス `lp`（Out-Printer）と衝突し、`(LP $x $y)` が黙って Out-Printer 呼び出しになる。検証が丸ごと空振りした

### v0.8.11（2026/07/27）
- **シークバー未読部分の色調整** — レッド #FF0000 → **少しオレンジ寄りの #FF3300**（不透明度15%は据え置き）。実測: 背景 RGB(85,107,47) 上でバー内側が RGB(110,99,40) となり、α=0.15 合成の計算値(110.5, 98.6, 40.0)と一致（旧色ならG=91）

### v0.8.10（2026/07/27）
- **シークバー: 未読部分に下地を追加** — 従来は未読部分が「黒1px輪郭＋内側透過」だったため、**黒背景の画像ではバーが完全に見えなくなっていた**。レッド（v0.8.11で #FF3300 に調整）を**不透明度15%（α=26）**で塗る（`SeekUnread` 新設）。z順は 未読下地→読了塗り→輪郭→サム（黒縁と読了塗りを潰さない順）。実測: 黒背景では暗赤でバー範囲が追える／白背景では淡いピンクで下の画像はほぼ透ける
  - **用語の注意（今回の解釈違い）**: ユーザーの「Red15%」は**不透明度15%**（完全透過=0%基準）の意。一方 v0.8.7 の「イエロー15%透過」は**15%透明＝不透明度85%**（α=D9）。**「N%透過」と「色N%」で基準が逆**なので、指定を受けたら不透明度がどちらなのか確認すること
- **シャープ化トグルを F11 → F10 に変更** — `ToggleSharpen` のデフォルトキー。F11は空きに
  - **🚨 F10 は Windows の「メニュー起動キー」**。WPFでは `e.Key == Key.System` / `SystemKey == F10` として届くため既存の変換で拾えるが、**放置するとメニューモードに入り以降のキー入力が無視される**。`Window_KeyDown` の末尾で `if (k == Key.F10) e.Handled = true;` を追加して消費する。`Key.System` 全般を消費すると Alt+F4 等を潰すため **F10 限定**にすること
  - **既存ユーザーへの影響**: 既に `ToggleSharpen=F11` を持つ ini は**その値が優先されるため F11 のまま**。デフォルト変更は新規ini/該当行削除時のみ効く。配備済み ini は手動で書き換えるか行削除が必要
- 実測検証: 実画面キャプチャで黒/白背景のバー意匠を確認、F10は**実キー経路（WM_SYSKEYDOWN）**でトグル動作＋押下後もキー入力継続、F11は無反応、iniに `ToggleSharpen=F10` 出力を確認
- **検証ノウハウ追記**: フルスクリーン時の**シークバーは PrintWindow では写らない**ことがある（アニメーション由来の合成レイヤ）。`Graphics.CopyFromScreen` で実画面を撮り、`GetWindowRect` で対象領域を切り出すこと。カーソルは「一度ゾーン外へ→数段階でゾーン内へ」移動させないと WM_MOUSEMOVE が出ず出現しない

### v0.8.9（2026/07/27）
- **再読み込みキー新設（F55）** — `ReloadCache`（デフォルト **`R`**、ini `[KeyBindings]` で変更可）。表示中フォルダを**再列挙**しつつ**デコード済みキャッシュを全破棄**して読み直す。外部での追加・削除・上書き編集（Ctrl+E で外部エディタ保存した結果など）を再起動せずに反映する。仕様は統合要件定義書 §23
  - 表示位置は現在ファイルを**パスで照合して維持**（前後にファイルが増減してもページ番号が追従）。削除されていた場合は同順位付近へフォールバックして通知に付記。ズーム倍率は維持、ナビ履歴はクリア
  - アーカイブモードでは展開済み内容が変わらないため**一覧は維持しキャッシュのみ破棄**（再展開はしない）
  - **設計上の要点**: `_clipFiles` を必ず新しい List インスタンスに差し替えること。背景デコード（先読み・アニメデコード）は書き戻し前に `ReferenceEquals(_clipFiles, files)` を確認する既存ガードがあるため、参照を変えるだけで実行中タスクの結果が新キャッシュを汚さなくなる。逆に同一インスタンスを使い回すと古い画像が書き戻される
  - `_animDecoding` は「実行中デコード」の進行フラグでありキャッシュではないためクリアしない（消すと二重デコード）
- **キャッシュクリアの共通化** — 同一内容の9行クリアがアーカイブ展開・兄弟ディレクトリ移動・ファイル削除の3箇所に重複していたため `ClearImageCaches()` に集約（キャッシュを増やしたとき片方だけ直し忘れる事故の予防）。列挙拡張子リストも `_viewerExtPatterns` に共通化
- **アイコン更新** — ユーザー更新版マスター（青系グラデーション）でICO再生成
- 実測検証: ①ファイル追加+現在ファイル上書き→R で「2/3・旧画像」→「3/5・新画像」に更新 ②現在ファイル外部削除→R で同順位へフォールバック ③アーカイブ閲覧中→R で一覧維持+ページ送り継続 ④アニメ再生中→R で再生継続（フレーム/再生モード表示も維持）

### v0.8.8（2026/07/23）
- **シークバー出現ゾーン修正** — ウィンドウモードで「実際のバー位置より下にカーソルを置かないと出ない」問題を修正。原因は判定基準が `Window.ActualHeight`（タイトルバー等の非クライアント領域込み）だったこと。ルートGridに `RootGrid` を命名し**クライアント領域基準の下端50px**に変更（フルスク/ウィンドウ共通）。実測: ウィンドウモードで下端25px=表示・70px=非表示を確認
- **アニメ情報表示の拡充** — アニメ表示中は情報表示ON（Basic以上）なら「フレーム: n/総数」「再生モード: …」を必ず表示、一時停止中のみ「一時停止中」を追加（並び=フレーム→再生モード→一時停止、`InfoAnimMode`/`InfoAnimPause` 新設、`UpdateAnimStatusInfo()`）。再生モード表示は実効値（_loop識別子→「ループ固定（_loop）」、_loopN→「ループ n/N回→自動遷移」、通常→「無限ループ」or「1ループ→自動遷移」）
- **_loop識別子の仕様変更（F53改）** — 判定を「ファイル名に loop を含む」から**「ファイル名末尾（拡張子除く）が `_loop` または `_loopN`」**（正規表現 `_loop(\d+)?$`、大文字小文字無視）に変更（LoRA名等に含まれる loop の誤爆防止）。`_loop`=ページ送りまで強制ループ（送り操作は現在のループを末尾まで再生後に遷移・再押下で即時・一時停止中は即時=従来同様）。**`_loopN`=N回ループ再生後に自動遷移**（`_gifLoopLimit`/`_gifLoopCount` 新設、再生モード設定より優先）。アニメの単ページ強制表示は従来実装（_knownAnimated+SpreadStepSize=1）をそのまま踏襲
- 実測検証: 通常アニメAutoAdvance遷移 / _loopの3ループ継続・保留遷移 / _loop2の2回後自動遷移 / 一時停止表示、いずれもテストGIF(8フレーム×100ms)で確認済み

### v0.8.6（2026/07/18）
- **BF04: 長パス画像が黒表示になる問題の修正** — v0.8.5の長パス対応後も、フルパス260文字超の画像だけ表示が真っ黒（ページ送り・情報表示は正常）だった。プローブexeでの実測により、**App.config の AppContextSwitchOverrides は「.NET側の門」を開けるだけで、素の長パスは Win32 CreateFile が MAX_PATH で拒否する**ことが判明（292文字の実在ファイルで File.Exists=false / FileStream=DirectoryNotFoundException、`\\?\` 付きなら両方成功）。対策: `LongPath.cs` 新設（`LongPath.Fix()`= 240文字以上のパスに `\\?\` を付与、UNCは `\\?\UNC\`）し、**画像パスを開く全箇所**（デコード・寸法取得・アニメ判定/再生・EXIF・クリップボード・コピー保存・zip展開・列挙）に適用。静止画デコードは `BitmapImage.UriSource`（WPFがWICネイティブAPIへパスを渡すため長パス不可）から **FileStream+StreamSource** に変更。地雷リストの MAX_PATH 項も更新
  - 既知の残制約: ごみ箱削除（VB FileSystem.DeleteFile=SHFileOperation）は `\\?\` 非対応のため260超パスでは失敗する（エラー通知は出る）。レジストリ LongPathsEnabled+マニフェスト対応は配布先環境に依存するため不採用
- **ini外部変更の自動再読み込み（F54）** — 起動中にiniを編集保存→ウィンドウの**アクティブ化（Activated）時点で自動反映**（再起動不要）。F2でエディタ→編集→Alt+Tabで戻る、の動線でそのまま反映される。仕様は統合要件定義書 §22
  - 実装: `IniFileManager` が自己書き込み時刻を記録し `HasExternalChange()`（mtime比較）で外部編集を検知。`TryParseForReload()` は**書き戻しなし**のパース（エディタで開いたままのファイルを裏で書き換えない）。読み取り失敗時は現状維持→次のアクティブ化で再試行
  - **[State] はアプリ所有**: 再読み込み時は `SyncStateToSettings()` で実行中の値を維持し、外部編集の反映対象は設定セクションのみ。フィルタ設定変更は `ApplyFilterToggle()` で背景再生成（F9トグルと同経路）
  - `Window_Closing` でもサイレント実行。**「起動中にini編集→アプリを閉じると PersistStateNow が編集前設定で上書きして編集消失」という既存の穴も同時に修正**（きっかけはユーザーのこの指摘）
  - キーディスパッチ（`Window_KeyDown`）は毎押下 `_settings` 直接参照のため、設定オブジェクト差し替えだけでキーバインドが即反映される。`_actionMap` はメソッド参照のみで再構築不要
- **検証の地雷（UI自動テスト）**: PostMessage 方式のキー送信は**ウィンドウのアクティブ化と同一スクリプト実行内で行うこと**。ツール呼び出しを分けると次の呼び出しのコンソールがフォアグラウンドを奪い、フォーカスなしの WPF は WM_KEYDOWN を無視する（今回これで30分溶けた）。SetForegroundWindow はフォアグラウンドロックで失敗しうるので、最小化→復元（ShowWindow 6→9）でのアクティブ化が確実

#### 構想: フィルタプロファイル化【2026/07/27 提案・ユーザー検討中（保留）】

ユーザー構想: 「レベル補正やモノクロ化などのフィルタを追加し、任意設定のフィルタを複数指定（単指定も可）して重ねたプロファイルを作成。フィルタ機能のON/OFFとプロファイルのトグル選択キーで操作する」。
Phase3（Area/Gaussian）はこの改修に相乗りさせる想定。**ユーザーが「もう少し考える必要がある」と保留中のため着手しないこと**（2026/07/27時点）。以下はAI側の設計案（叩き台）。

- **フィルタを2クラスに分けるのが設計の要**:

  | クラス | 中身 | 適用条件 | 順序 |
  |---|---|---|---|
  | リサンプル系 | モアレ軽減（Lanczos/Area/Gaussian）、シャープ化 | 縮小表示時のみ（現行ゲート維持） | 固定（デコード時の粗縮小と結合しているため） |

- **性能**: トーン系はレベル補正・反転・彩度を1本のLUTに畳み、モノクロ化（チャンネル混合）まで含めて1パスで処理できる。既存のLanczos縮小より遥かに軽いので重ね数によるコスト増はほぼ無い
- **ini案**: `[Filters]` に `FilterEnabled` / `ActiveProfile` / `MoireDownscaleThreshold`、`[FilterProfileN]` に `Name` / `Stages=Moire,Sharpen,Levels,Mono` / `Moire.Strength=40` 形式のパラメータ。旧 `[Filters]` の値は初回読み込みで `FilterProfile1`（名前=既定）へ自動変換すればユーザー作業ゼロで移行できる
- **キー案**: F9=フィルタ全体ON/OFF、F10=次プロファイル、F12=前プロファイル（F10/F12は元々この用途で予約済み）、F11は空きに。切替時はプロファイル名を通知＋情報パネルにも表示

### 2-4. S2CSP連携受け口【将来実装・2026/07/24 要件定義済み】

  - 新セクション `[S2CSP]` を ini に追加

```ini
[S2CSP]
Enabled=0                    ; 配布デフォルトOFF（既存動作維持）
ExePath=                     ; 空欄=標準探索、絶対パスで固定も可
HotKey=                      ; 割当キー（実装時に空きキーから確定、§5参照）
FallbackToShellOpen=1        ; 未検出時に既存「指定アプリで開く」へフォールバック
```

- **実装順序**: S2CSP 本体の実装完了・実運用検証が済んだ後に ClipViewer 側受け口を実装する
- **要注意事項**:
  - `HotKey` のデフォルト値は既存キーマップ（§5空きキー一覧参照）と衝突しないよう実装時に確定
  - S2CSP.exe 探索順序（ini指定 → PATH → 既定インストール場所）は実装時に確定
  - アーカイブ内展開ファイル（`%TEMP%\ClipViewer\` 配下）を送信対象とする場合、S2CSP 側での TEMP 掃除タイミングとの相互作用に注意

### 🚨 Alt+Key が取得できない問題
**症状**: Alt+Right 等の Alt 修飾キーを押すと `e.Key == Key.System` になり、実キーが取れない。  
**原因**: WPF の仕様。Alt キー押下時は `e.Key` が `Key.System` に上書きされる。  
**解決策**: 以下のように `e.SystemKey` で実キーを取得する。

```csharp
Key k = (e.Key == Key.System) ? e.SystemKey : e.Key;
```

**症状**: `using Microsoft.VisualBasic.FileIO;` を追加すると `SearchOption` が `System.IO.SearchOption` と `Microsoft.VisualBasic.FileIO.SearchOption` で ambiguous エラー (CS0104) になる。  
**解決策**: `using` を追加せず、`DeleteFile` を完全修飾名で呼ぶ。

// NG: using Microsoft.VisualBasic.FileIO; を追加する
// OK: 完全修飾名で呼ぶ
Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile(

);

### 🚨 AI生成画像の巨大メタデータで UI が数十秒フリーズする問題【2026/07/10 根治】
**症状**: 情報パネルが Detailed モード（EXIF表示）のとき、AI生成画像（Stable Diffusion / ComfyUI 等の出力）を含むフォルダで起動やページ送りが30〜40秒フリーズする。
**原因**: AI生成画像はメタデータ（Comment等）に数百KB級のプロンプト/ワークフローJSONを埋め込む。それをそのまま `TextBlock`（`TextWrapping=Wrap`）に流すと、WPFのテキストレイアウトがUIスレッドを数十秒占有する。
**解決策**: `ReadExifSummary()` で各メタデータ項目を切り詰めてから表示する。**メタデータ由来の文字列を無制限に TextBlock へ渡さないこと。**
（上限は使用感フィードバックで調整済み: 撮影日40/機種60/タイトル800/コメント800文字、全体1000文字。1000字程度ならレイアウトは1秒未満で問題ない）
**補足**: AI生成画像のプロンプト/ワークフローJSONは **Title（EXIF ImageDescription、タグ270）に入っていることが多い**（ComfyUI 等、実測5万文字）。Comment は空のことが多いので、切り詰め調整時は Title 側を忘れないこと。
**教訓**: この問題は長らく「exeをコピーし直すと直る謎の遅延」として誤認されていた。実際は復旧儀式の ini 削除で `LastInfoMode` が Basic にリセットされていたのが「治った」理由。症状と対処の因果は startup.log（起動診断ログ）で確定した。

### 🚨 MAX_PATH超のパスで Path API がクラッシュ（v0.8.5で修正）→ 画像が黒表示（v0.8.6で完全修正）
**症状**: ①特定フォルダを開くとアプリが即クラッシュ（v0.8.5で修正）②その後も260文字超の画像だけ真っ黒表示（v0.8.6で修正）。
**原因**: ①AI生成画像の長大ファイル名でフルパスが260文字を超えると `Path.GetDirectoryName` 等が `PathTooLongException` → NaturalSort 比較器内で発生し `List.Sort` ごとプロセス中止 ②**App.config の長パス有効化（AppContextSwitchOverrides）は .NET 側の制限を外すだけで、素の長パスは Win32 CreateFile が MAX_PATH で拒否する**。`LoadImageCore` の catch が例外を握り潰して黒表示になっていた。
**解決策**: ①比較器はパスAPIを使わず `LastIndexOf('\\')` + `Substring` の純粋文字列操作に変更 ②App.config（新パス処理）は維持した上で、**ファイルを開く直前に `LongPath.Fix()` で `\\?\` プレフィックスを付与**（240文字以上のみ）。WPF の `BitmapImage.UriSource` は WIC ネイティブへパスを渡すため長パス不可 → **FileStream+StreamSource** でデコードする。
**教訓**: ホットパスでは例外を投げ得る Path API を避け文字列操作で。長パスは「.NET の門」と「Win32 の門」の**二重扉**であり、AppContext スイッチだけでは開かない（実測で File.Exists が false を返す）。新しいファイルI/O追加時は `LongPath.Fix()` を通すこと。「解決したはず」の対策は**実物パスでの実測**まで閉じること（v0.8.5 はクラッシュ消失のみ確認し、長パス画像の表示成功は未確認だった）。

---

### 🚨 PowerShell のテキスト往復でソースの日本語が化けて焼き付く（2026/07/19 実害）
**症状**: ソースファイルの日本語コメントが「繧ｷ繝ｼ繧ｯ」のような文字化けでファイルに恒久保存される。ビルドは通るため気づきにくい。
**原因**: PowerShell 5.1 の `Get-Content` は **BOM なし UTF-8 を ANSI(Shift-JIS) として誤読**する。`Get-Content → -replace → Set-Content` の往復で化けた文字列がそのまま書き戻される。一部の化け文字は置換不能文字を含み、Edit ツールでのマッチすら不可能になる。
**回避策**: **ソースファイルの文字列置換は必ず Edit ツール、全文書き直しは Write ツールを使う**（エンコーディング安全）。PowerShell でファイル内容に触れてよいのは読み取り専用の検査か、ASCII のみと確認済みのファイルだけ。
**復旧手順**: `[regex]::Matches($txt,'[繧繝縺]')` で化けを検出 → git／公開リポジトリのクリーン版から復元 → 復元後に化け残存ゼロを機械チェックで確認。v0.8.7 開発時に MainWindow.xaml（コメント97文字）・csproj・AssemblyInfo(©) をこれで破損させ、ClipViewer-github のスナップショットから復旧した。
**教訓**: 「ビルドが通る＝無傷」ではない。テキストを書き戻す操作は必ずエンコーディングを意識し、書き戻し後に化け検出チェックを挟むこと。

### 🚨 Claude側制約: Write前にRead必須
**症状**: `Write` ツールで既存ファイルを上書きしようとすると `File has not been read yet. Read it first` エラーになる。  
**回避策**: 既存ファイルの書き直し前に必ず `Read` を1回実行してからWrite。新規ファイルなら不要。  
※ これは Claude/Cowork の制約であり、コード側の問題ではない。

## 4. ini 移行メモ

### v0.5.x → v0.6.0 における手動更新が必要な項目

#### SaveDirectory のデフォルト変更

v0.6.0 から **デフォルト値が変更**された。既存 ini を引き継ぐ場合、手動で以下を書き換えること。

```ini
; 旧値 (v0.5.x) — 固定パスがデフォルトだった
SaveDirectory=C:\<任意の作業フォルダ>

; 新値 (v0.8.0〜) — ピクチャ\ClipViewer が既定
SaveDirectory=%USERPROFILE%\Pictures\ClipViewer
```

> **注意**: アプリが ini の旧値をそのまま読み込むため、自動更新はされない。  
> ini を削除して再生成するか、テキストエディタで直接編集すること。

#### [MouseBindings] セクションが自動追加される

v0.6.0 以降、ini 書き込み時に `[MouseBindings]` セクションが自動付与される。  
既存 ini への初回書き込み時（設定変更・正常終了時）に追記される。

### v0.8.9 → v0.8.10: ToggleSharpen のデフォルトキー変更（F11 → F10）

**キーバインドのデフォルト値変更は、既存 ini には適用されない**（ini の値が常に優先されるため）。
既存 ini で F11 のまま使い続けたくない場合は、以下のいずれかを行う。

```ini
; 手動で書き換える（推奨・F2 で開いて編集 → ウィンドウに戻れば即反映）
ToggleSharpen=F10
```

または `ToggleSharpen=` の行を削除して再生成させる（削除した行はデフォルト値で書き戻される）。
※ 新規追加キー（例: v0.8.9 の `ReloadCache`）は既存 ini に**自動追記される**ので対応不要。
　「既存キーのデフォルト値変更」だけがこの手当てを要する。

## 6.5 設計原則（ユーザー承認済み・2026/07/12）

**「重い処理が必要になるかの判定を最優先で済ませ、その後に他の処理を行う」**

表示経路を分岐させる判定（例: アニメか静止画か）は、可能な限り安く・早く確定させる。
- 判定が安価にできる場合（WebP=ヘッダ21バイトのVP8Xフラグ）→ **同期で即判定**し、初回表示から正しい経路に直行する
- 判定自体が重い場合（GIF=ファイル構造の走査が必要）→ **暫定表示+背景判定→確定後に再表示**へ逃がす
- 重い処理（アニメの初回フレームデコード等）が始まったら、競合する背景処理（先読み等）は**確定まで保留**して最優先リソースを確保する

v0.8.2 のアーカイブ+見開きモードでのアニメ開始遅延改善は、この原則の適用例。新フォーマット対応や新機能でも同じ基準で設計すること。
